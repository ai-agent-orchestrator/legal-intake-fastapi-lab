LangChain·LangGraph·LangSmith·RAG·임베딩·벡터 RAG·memvid를 모두 개발 범위에 포함한다. 첫 목표는 합성 상담 준비 안내문 10개에서 근거를 찾아, 출처가 있는 안내 답변 하나를 만드는 것이다. 큰 시스템부터 만들지 않고 같은 작은 예제를 일곱 개념으로 끝까지 이해한다.

현재와 앞으로를 구분합니다.

현재 개발 브랜치에는 기존 API 3개와 L01/L02 문맥·세션 위험 코드가 있으며 실제 NeMo를 포함한 95개 테스트를 통과했다. 이 문서의 LangChain·LangGraph·LangSmith·임베딩·memvid 검색은 앞으로 만들 설계다. 이 화면의 비교 체험은 고정된 학습 예시이며 실제 모델이나 검색기를 실행하지 않는다.

먼저 개발 전 구조 설계안을 Claude에게 검수한다. Claude 전달 요청서의 형식으로 피드백을 받고, 지적 사항을 반영한 최종 개발안이 확정된 뒤 구현한다. 이 문서만으로 구현 착수를 승인한 상태는 아니다.

3. 첫 번째 사용 사례

질문은 “집주인이 돈을 안 돌려줘요. 상담 전에 뭘 준비하죠?”로 시작한다. 저장된 “임대차 보증금 반환 상담 준비” 안내문에서 계약서·입금 자료·사건 경위 정리 항목을 찾는다. 답변에는 준비자료와 확인할 질문, 사용한 문서 ID를 포함한다. 법률 판단·승소 확률을 생성하는 서비스로 확장하지 않는다.

처음 저장할 문서는 합성 안내문 10개다. 접수 원문과 개인 사건 기록을 검색용 지식으로 자동 적재하지 않는다. 후기·게시글의 분석은 이후 별도 자료 구분을 두고 추가한다. 후기를 공식 안내 근거처럼 섞지 않는다.

4. 적재와 질문 응답은 두 흐름이다

적재는 미리 한 번, 질문 응답은 요청마다 실행한다. 같은 문서를 질문마다 다시 임베딩하지 않는다.

미리 준비하기 · 적재

  1. 합성 안내문 읽기
  2. 입력 검사·개인정보 마스킹
  3. 제목·문단 단위 분할
  4. E5 문서 임베딩
  5. memvid 저장

사용자가 질문할 때

  1. 요청 문맥·세션·입력 검사
  2. 마스킹한 질문 임베딩
  3. memvid 검색
  4. LangGraph 근거 분기
  5. LangChain + Llama 생성
  6. 출력 검사 후 반환

검색 결과도 외부에서 온 데이터처럼 다룬다. 자료에 “검사를 생략하라”는 문장이 있어도 시스템 지시로 승격하지 않는다. 마스킹과 보안 검사는 그래프 안의 LLM이 임의로 생략할 수 없도록 서비스 경계에서 강제한다. LangSmith는 이 흐름의 단계별 실행을 기록하되 원문을 보내기 전에 기록 데이터도 처리한다.

5. 키워드 검색과 벡터 검색 비교하기

최소 개념: 벡터와 코사인 유사도

벡터는 임베딩 모델이 문장을 표현한 숫자 배열이다. 코사인 유사도는 두 벡터의 방향이 얼마나 비슷한지 비교하는 기준이며, 같은 모델 공간에서 관련 자료 후보를 정렬할 때 사용한다. 유사도는 정답 확률이나 법률적 정확도가 아니다. top-k는 가져올 후보 수이며 근거의 충분함과 다르다. 이번에는 Legal Intake 이해를 위한 개념 공부로 제한한다. 별도 리서치 시스템, 개인 검색식, Llama 질의 요약기나 맞춤 랭킹 설계는 추가하지 않는다. LangChain의 벡터 유사도 검색 설명.

키워드 검색은 표현이 겹치는 자료를 찾고, 벡터 검색은 임베딩의 유사도를 사용한다. 법률 용어·문서 번호가 정확한 질문에는 키워드가 유용하고, 일상어로 바꿔 말한 질문에는 의미 검색이 도움이 될 수 있다. 처음에는 두 방식을 따로 비교한다. 어느 방식이 좋은지는 우리 평가 질문으로 확인한다.

학습용 고정 예시 · 실제 임베딩/검색 실행 아님
키워드 · 표현이 다르면 놓칠 수 있어요

고정 예시에서는 일치 문서가 없습니다. 실제 결과는 토큰화·문서 내용·검색 설정에 따라 달라집니다.

LangGraph → 근거 없음 → 추가 자료 요청

혼합 검색은 후속 비교 단계다. 두 결과를 합칠 때 점수 체계가 다른 값을 그대로 더하지 않는다. 기본 실습에서는 먼저 키워드/벡터를 선택하도록 만들고, 혼합은 순위 기반 결합의 효과를 확인한 뒤 활성화한다.

6. 임베딩 선택 · Llama 생성과 E5 검색

대표님이 정한 Qwen 제외 방침을 반영해 Qwen 모델은 기본 실행 후보에서 제외한다. 생성 모델은 Llama 계열, 검색 임베딩의 우선 검토 모델은 intfloat/multilingual-e5-large-instruct로 정한다. 이 조합은 모델 계열이 달라도 가능하다. 임베딩은 숫자 벡터를 만들고 Llama는 검색한 텍스트를 읽어 답한다. 현재 저장소의 실제 생성 client는 OpenAI SDK이므로 Llama 실행 어댑터는 앞으로 추가할 작업이다.

E5의 개발 주체는 Microsoft 연구진이며 intfloat는 배포 계정명이다. Microsoft 소속이 명시된 기술 보고서와 Microsoft 공식 E5 저장소에서 확인한다. Microsoft가 이 프로그램의 실행을 대신 맡거나 데이터를 자동 보호한다는 의미는 아니다.

OpenAI small/large 표는 별도 비교 항목이다

text-embedding-3-small과 text-embedding-3-large는 E5·Qwen과 다른 OpenAI API 모델이다. 기본 차원은 각각 1536·3072이며 요청 시 차원을 줄이는 기능이 있다. OpenAI 공식 임베딩 안내. 전달받은 14/20·19/20, 18/20·20/20 수치는 평가 질문·문서·top-k·지표 이름이 없어 일반 성능이나 우리 프로젝트 실측 결과로 인용하지 않는다. 현재는 확인 불가다. 외부 API 임베딩은 Llama 생성과 함께 쓸 수 있지만 텍스트가 해당 API로 전송된다. 기본안은 로컬 E5 우선 검토를 유지하고, 원격 API는 검토 가능한 대안으로만 둔다.

이번 채택 우선 구현·한국어 검색 평가 대상 비교 설명만 포함, 실행하지 않음

위 사양의 근거는 E5 모델 카드와 Qwen 모델 카드다. 벡터 차원이 크거나 모델이 크다고 우리 한국어 상담 질문에서 항상 더 잘 찾는다는 뜻은 아니다. 두 모델의 같은 데이터·같은 조건의 한국어 법률 검색 우열은 아직 측정하지 않았다.

E5의 핵심 주의점은 512 토큰 제한이다. 처음에는 E5 tokenizer 기준 300토큰 청크·40토큰 겹침을 실험 시작값으로 사용하고 제목과 문단을 보존한다. 질문 instruction을 포함한 최종 입력도 길이를 확인한다. 이는 확정 최적값이 아니며, 긴 문서를 통째로 넣어 뒤가 잘리는 방식을 피하기 위한 기본값이다. 문서와 질문에는 같은 E5 모델 revision·차원·정규화 규약을 쓴다. 모델을 바꾸면 새 .mv2 인덱스를 만들고 재임베딩하며 기존 벡터를 혼합하지 않는다.

메모리는 정밀도·배치·장치·길이에 따라 달라진다. 단순 가중치 계산으로 0.6B × 2바이트는 약 1.2GB, 8B × 2바이트는 약 16GB이며 실제 실행에는 여기에 추가 메모리가 든다. 이 수치는 필요한 GPU 메모리 보장값이 아니다. 이 PC에서 E5/Llama의 동시 실행 속도와 메모리는 아직 확인하지 않았다.

보안은 개발사와 실행 경로를 따로 확인한다

공식 모델을 내려받아 로컬 추론하는 방식과 외부 임베딩 API를 호출하는 방식은 다르다. E5도 외부 호스팅 API를 쓰면 텍스트가 그 제공자에게 전송될 수 있다. 로컬 Qwen 실행을 두고 근거 없이 중국으로 데이터를 보낸다고 단정하지 않는다. 이번 설계는 대표님의 Qwen 제외 방침을 따른다.

실행 설계는 고정 revision의 공식 가중치·검토한 패키지·로컬 추론을 우선한다. 임의 원격 코드 실행 옵션을 켜지 않고, 모델을 준비한 뒤 오프라인 로딩·외부 전송 여부를 검증한다. 임베딩도 원문에서 유래한 데이터이므로 공개 산출물로 자동 업로드하지 않는다. LangSmith 원문 추적을 켜면 로컬 Llama/E5 구성에서도 데이터가 외부로 나갈 수 있으므로 별도로 제어한다.

7. memvid와 retriever의 연결

memvid는 마스킹한 안내문 청크·출처·버전·임베딩을 저장한다. Windows에서 memvid SDK의 내장 로컬 임베딩 제한을 피하기 위해, 별도 E5 provider에서 벡터를 만든 뒤 memvid에 외부 벡터로 전달하는 어댑터를 설계한다. 실제 설치 버전의 저장·질의 기능을 먼저 통합 시험한다. memvid SDK 공식 안내는 외부 임베딩과 질의 벡터 전달을 설명한다.

데이터 저장할 내용
본문 마스킹된 청크 텍스트
출처 documentId, chunkId, title, sourceVersion
모델 embeddingModel, pinnedRevision, dimension, normalization
범위 collectionId=synthetic-guides-v1, documentType=guide
운영 기준 적재 실행 ID와 활성 인덱스 버전

MemvidRetriever는 질문을 받아 Document 목록으로 반환하는 내부 어댑터다. 생성 모델은 벡터가 아니라 검색된 텍스트를 읽는다. memvid의 직접 답변 생성 함수를 사용해 우리 출력 검사를 우회하지 않고, 검색 결과를 기존 서비스로 되돌린다. 관련 자료가 없으면 임의 문서를 억지로 근거로 붙이지 않는다. 관련성 기준은 고정 cosine 0.8처럼 임의로 정하지 않고 합성 평가 질문으로 보정한다. 항상 top-k 결과가 나온다는 사실만으로 근거가 있다고 판단하지 않는다.

8. LangGraph는 작은 분기 하나부터

첫 그래프는 반복 없이 끝나는 고정 workflow다. 요청마다 별도 state를 만들며 초기 버전에서는 대화 checkpoint와 영속 대화 기억을 사용하지 않는다. 세션 위험 저장소와 그래프 state는 서로 다른 책임이다.

START → retrieve → 근거 유무 확인
                  ├─ 있음 → generate → END
                  └─ 없음 → ask_for_materials → END
node 입력 → 출력 호출 규칙
retrieve safeQuestion → 근거 청크·출처 memvid 검색 1회, vector 모드일 때 질문 임베딩 1회
generate 질문·근거 → 구조화 초안 LangChain chain + Llama, 최대 생성 1회
ask_for_materials 질문 → 추가 자료 요청 템플릿 LLM 생성 0회

graph 안에 보안 우회 분기는 두지 않는다. 입력/출력 검사와 유료 단계의 용량·예산·취소 정리는 서버 서비스가 감싸서 보장한다. 오류를 “근거 없음”으로 숨기지 않고 기술 오류로 구분한다. 자동 재시도·재검색 루프는 첫 범위에서 제외한다. LangGraph 재실행으로 같은 유료 호출이 중복 실행되지 않는지 후속 영속화 도입 전에 별도로 설계한다.

9. LangChain · 메시지·LCEL·구조화 출력

LangChain에서는 시스템 지시·사용자 질문·검색 근거의 역할을 구분하는 템플릿을 만든다. 자료를 구분자로 넣는 것만으로 injection이 해결되지는 않으므로 별도 입력 검사를 통과해야 한다. LCEL은 이 짧은 node의 연결에 사용하고 전체 업무의 분기는 LangGraph가 담당한다.

검색 근거 정리 → ChatPromptTemplate → Llama 모델 어댑터 → Pydantic 검증

구조화 출력은 내부 DTO에 먼저 적용한다. 생성 모델의 native schema 지원 여부를 확인하고, 지원하지 않으면 JSON 출력과 서버 Pydantic 검증으로 동작시킨다. 실패한 출력을 그대로 공개하지 않는다. JSON 형식이 맞아도 사실·안전성이 맞는 것은 아니다.

{
  "answer": "상담 전에 계약서와 입금 자료를 정리하세요.",
  "preparationItems": ["계약서", "입금 자료"],
  "questions": ["현재 보유한 자료가 무엇인가요?"],
  "citationIds": ["GUIDE-001:chunk-01:v1"],
  "evidenceStatus": "FOUND"
}

서버는 citationIds가 실제 검색 결과의 ID 부분집합인지 확인한다. 자료가 없으면 evidenceStatus=NOT_FOUND와 빈 출처를 서버가 확정하고 추가 자료 안내를 보낸다. 현재 API의 answer/model/intakeId 계약은 유지하고, 새 필드는 내부 평가에 먼저 사용한다. 외부 응답 확장은 별도 계약 변경으로 검토한다. 구조화 출력 공식 문서.

10. LangSmith는 추적과 평가로 반드시 사용한다

개발 완료 기준에 실제 LangSmith trace 확인과 합성 데이터 평가 실험을 포함한다. SDK를 설치한 것만으로 연동 완료라고 하지 않는다. 키가 없는 환경에서는 local 시험이 가능하지만 LangSmith 원격 연동 완료 상태와 구분한다.

기본 trace 구성은 request → graph → retrieve / generate / validation이다. 기록할 값은 요청 trace ID, node 이름, 문서 ID, 검색 모드, 시간, 결과 코드, 모델·프롬프트·인덱스 버전이다. 기존 session 원문·전화·이메일·실제 사건 내용·키·원문 예외를 metadata나 오류에 넣지 않는다. 입력·출력은 기본 숨김으로 시작하고, 합성 평가 데이터에 한해 명시적으로 내용을 기록한다. LangSmith 입력·출력·metadata 처리를 적용한다.

평가 첫 기준
검색 질문 20개 중 기대 문서가 top-3 안에 있는 비율: Hit@3
무근거 분기 근거 없는 질문은 생성 0회·출처 비어 있음
출처 응답의 모든 ID가 실제 검색 결과에 포함됨
안전성 합성 PII가 저장·전송·응답·trace에 남지 않음
지연 질문 임베딩·검색·생성 시간을 구분해서 측정
비용·사용량 원격 임베딩/생성 사용량과 로컬 자원 사용을 구분

초기 목표 예시는 Hit@3 80% 이상이지만 아직 달성한 결과가 아니다. 평가 질문 20개와 별도 확인 질문 10개를 두고, 청크/모델 변경은 같은 질문으로 비교한다. 처음에는 코드 평가와 사람의 확인을 사용하며 LLM judge 비용은 필수로 만들지 않는다. LangSmith 장애는 보안 검사 실패와 구분한다. 기록 실패가 생겨도 보안 검사를 생략하거나 원문을 실패 로그에 다시 출력하지 않는다. LangSmith 평가 공식 문서.

로컬 E5/Llama에는 공급자 토큰 요금이 없더라도 계산 자원·동시성·timeout 제어는 필요하다. 원격 임베딩을 선택하면 생성과 별도의 비용 예약 단계를 거친다. trace 비용 표시는 예산 원자 예약을 대신하지 않는다. 네트워크·native 동기 호출은 async node 안에서 직접 블로킹하지 않도록 비동기 client 또는 제한된 worker로 분리한다.

LangChain·LangGraph·LangSmith·memvid·E5 실행 의존성은 실제 조합을 설치·시험한 후 전용 runtime lock에 고정한다. 이번 설계 문서 작업에서 모델을 내려받거나 패키지를 새로 설치하지 않았다. Llama의 정확한 모델 ID·정밀도·실행 서버는 하드웨어와 운영 조건을 확인한 뒤 정한다.

13. 앱 API는 최대 11개

기존 API 3개와 다음 확장 8개를 합친 기본 구성으로 정한다. 이 목록은 목표 계약이고 현재 브랜치에서 실행되는 API는 기존 3개다. 내부 적재·검색·평가는 별도 공개 API를 늘리지 않는다.

구분 메서드·경로 개수
기존 접수 POST /api/intakes, GET /api/intakes/{intake_id}, POST /api/intakes/{intake_id}/guidance 3
상태 GET /health 1
게시글 POST·GET /api/posts, GET /api/posts/{postId} 3
후기 POST·GET /api/posts/{postId}/reviews 2

기존 상세 설계·api-catalog.json의 21개는 이전 후보 목록이다. 이번 기본 구성에는 독립 Chat/SSE·게시글 수정/삭제·단독 guardrail 시험 API를 추가하지 않는다. 동기/비동기 비교는 별도 학습 앱에서 진행한다. 이 설계로 인증·인가 범위를 확대하지 않는다.

14. 공부할 때 스스로 설명해 보기

LangChain과 LangGraph를 모두 쓰면 역할이 겹치지 않나요?

LangChain은 node 안의 프롬프트·모델·retriever 부품, LangGraph는 그 node의 순서와 분기를 담당합니다. 전체 서비스의 필수 보안 경계는 별도로 유지합니다.

memvid가 있으면 임베딩이 필요 없나요?

키워드 검색만 할 때는 임베딩 없이도 시작할 수 있습니다. 이번 목표인 벡터 RAG는 E5로 문서와 질문의 벡터를 만들어 사용합니다.

Llama로 생성하면 임베딩도 Llama여야 하나요?

아닙니다. E5로 찾은 문서 텍스트를 Llama에 전달할 수 있습니다. 문서와 검색 질문의 임베딩 모델은 서로 일치해야 합니다.

임베딩 모델을 바꾸면 같은 1024차원끼리 섞어도 되나요?

안 됩니다. 차원이 같아도 의미 공간과 전처리 규약이 다를 수 있습니다. 새 revision·모델은 별도 인덱스로 적재·평가합니다.

JSON 스키마가 맞으면 답변도 정확한가요?

형식과 내용의 정확성은 다릅니다. 실제 근거 ID 검사, 정책 검사, 사람이 확인하는 평가를 함께 수행합니다.

로컬 모델이면 LangSmith도 자동으로 로컬인가요?

아닙니다. 로컬 추론과 trace 전송 목적지는 별개입니다. 기본 원문 숨김을 유지하고 원격 연결과 합성 평가를 따로 검증합니다.
