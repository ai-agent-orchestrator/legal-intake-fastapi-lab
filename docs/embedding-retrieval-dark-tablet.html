1. 임베딩 기반 검색과 의미 기반 검색

의미 기반 검색은 문장의 뜻이 가까운 자료를 찾으려는 목표이고, 임베딩 기반 검색은 그 목표를 숫자 벡터로 구현하는 방법입니다. 모든 의미 검색이 반드시 같은 임베딩 방식을 쓰는 것은 아닙니다. 이번 프로젝트에서는 E5로 임베딩 기반 의미 검색을 구현합니다.

예를 들어 질문이 ‘집을 비웠는데 맡긴 돈을 못 받았어요’이고 문서 제목이 ‘임대차 보증금 반환 준비’라면 표현이 달라도 관련 자료를 찾는 것이 목표입니다. 실제로 잘 찾는지는 평가로 확인해야 합니다. 모델이 법률적으로 옳음을 이해하거나 보장하는 것은 아닙니다.

‘키워드 검색’도 구현 방법이 여럿입니다. 단순 부분 문자열 검사, 역색인, BM25 등을 같은 것으로 생각하지 않습니다. 이번 기준선은 memvid lex이며 점수를 BM25의 특정 구현이라고 단정하지 않습니다.

memvid 2.0.160의 기본 lex는 여러 단어를 모두 만족하도록 검색하는 동작이 관찰됐습니다. 따라서 비교 실험에서는 접수 문장 전체를 그대로 넣는 대신 추출한 토큰을 보증금 OR 반환 OR 계약서처럼 연결합니다. caseType 라벨, [PHONE]·[EMAIL], OR/AND/NOT 입력 토큰은 제외합니다. 한국어 형태소 분석은 추가하지 않으므로 ‘반환’과 ‘반환이’가 다르게 처리될 수 있습니다. 이 제한도 결과 해석에 포함합니다.

이번에는 lex와 vector 두 방식만 비교합니다. 혼합·RRF·나만의 가중식은 구현하지 않습니다.

3. 코사인 유사도: 방향이 얼마나 가까운가

벡터 A와 B의 코사인 유사도는 다음과 같습니다.

cosine(A, B) = dot(A, B) / (length(A) × length(B))

dot(A, B) = A의 첫 수×B의 첫 수 + A의 둘째 수×B의 둘째 수 + ...
length(A) = sqrt(A의 각 수를 제곱해서 더한 값)

수학적인 범위는 -1~1입니다. 같은 방향은 1, 직교 방향은 0, 반대 방향은 -1입니다. 이는 설명용 기하 관계이며, 실제 문장 임베딩에서 0이 곧 ‘무관’, 음수가 곧 ‘반대 뜻’이라는 규칙은 아닙니다.

벡터의 길이를 1로 정규화했다면 분모가 1이므로 내적이 코사인 유사도와 같습니다. 서로 다른 임베딩 모델의 벡터끼리는 비교하지 않습니다. 같은 차원이라고 같은 의미 공간이 되는 것도 아닙니다.

memvid가 반환한 score를 코사인 원값이라고 표시하지 않습니다. 합성 단위 벡터 실험에서 동일/직교/반대 벡터의 native score는 1 / 약0.293 / 0으로 관찰됐습니다. 원래 코사인 1 / 0 / -1과 다릅니다. 이번 평가에서는 native score로 임계값을 보정하며, 0.8 같은 공통 정답 기준을 가정하지 않습니다.

4. 의미 검색을 직접 구현하는 최소 코드

아래는 코사인 계산과 정렬 자체를 직접 작성한 학습 코드입니다. 벡터를 만드는 E5와 검색 엔진을 사용하는 production adapter는 별도입니다. 예시 숫자는 장난감 벡터이며 실제 문장 검색 성능이 아닙니다.

import math

def cosine(a, b):
    if not a or len(a) != len(b):
        raise ValueError("같은 차원의 비어 있지 않은 벡터가 필요합니다")
    if not all(math.isfinite(x) for x in [*a, *b]):
        raise ValueError("유한한 숫자만 사용합니다")
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(x * x for x in b))
    if norm_a == 0 or norm_b == 0:
        raise ValueError("길이가 0인 벡터는 비교할 수 없습니다")
    return dot / (norm_a * norm_b)

query_vector = [1.0, 0.0]  # 설명용 2차원 숫자
documents = {"A": [1.0, 0.0], "B": [0.0, 1.0]}
ranked = sorted(
    [(doc_id, cosine(query_vector, vector))
     for doc_id, vector in documents.items()],
    key=lambda item: item[1], reverse=True,
)
print(ranked)  # [('A', 1.0), ('B', 0.0)]

실제 연결 순서는 문서 청크 → E5 문서 임베딩 → 저장, 질문 → E5 질문 임베딩 → 검색 → 출처 확인입니다. E5의 질문에는 고정 instruction을 붙이고 문서에는 붙이지 않습니다. 문서·질문은 같은 모델 revision·차원·정규화 규약을 사용합니다. 현재 모델 입력 최대 512토큰, 청크 최대 300토큰, 겹침 목표 40토큰입니다.

소수 문서의 학습 코드는 모든 벡터를 하나씩 비교해도 됩니다. 벡터 스토어는 저장·인덱싱·검색을 담당하는 부품입니다. 현재 30개 청크에서 시작하는 목적은 복잡한 대규모 검색 시스템을 만드는 것이 아니라 각 단계를 관찰하는 것입니다.

5. Golden Set: 내가 아는 정답으로 평가하기

Golden Set은 질문과 그 질문에 관련 있는 정답 문서 ID를 사람이 확인해 고정한 평가 자료입니다. 원하는 답변 한 문장만 적는 것과 다릅니다. 검색 평가라면 ‘어떤 문서를 찾았는가’가 정답 계약입니다.

질문 ID 합성 접수 요약 정답 documentId 유형
예시 P 집을 비웠는데 맡긴 돈을 못 받음 G02 의역
예시 L 차용증 없는 대여금 상담 준비 G01 법률 용어
예시 N 안내문에 없는 요리법 질문 빈 집합 무근거

실제 고정본은 fixtures/rag/evaluation.json입니다. clientName은 검색에서 제외하고 다른 필드를 정해진 순서로 결합·예제 마스킹합니다. 정답은 문서 ID의 집합이므로 한 질문에 여러 관련 문서가 있을 수도 있습니다.

우리 자료는 비교20(근거14/무근거6), 확인10(근거6/무근거4)입니다. 확인10은 기존 파일의 split=holdout에 해당합니다. 의역·법률 용어·합성 PII 태그는 중복될 수 있어 유형별 개수를 합하면 전체보다 클 수 있습니다.

6. 임베딩 모델을 공정하게 비교하는 순서

  1. 문서·청크·질문·정답 ID·평가 지표를 먼저 고정합니다.
  2. 각 모델의 공식 입력 규약을 따릅니다. 한 모델의 instruction을 다른 모델에 그대로 쓰지 않습니다.
  3. 모델마다 문서와 질문 벡터를 새로 만듭니다. 서로 다른 모델의 벡터 인덱스를 섞어 쓰지 않습니다.
  4. 같은 Golden Set에서 문서 단위 Hit@1·Hit@3, 무근거 오판, 유형별 실패, 지연을 계산합니다.
  5. 임계값은 비교 자료로만 보정합니다. 확인 자료로 결과를 본 뒤 재조정하면 그 자료는 더 이상 독립 확인 자료가 아닙니다.
  6. 품질과 실행 부담을 함께 봅니다. 모델 이름·크기·차원만으로 한국어 검색 우열을 결정하지 않습니다.

이번 개발에서 실제 실행하는 임베딩 모델은 E5 하나입니다. lex와 E5 vector 비교가 임베딩 모델 여러 개의 비교는 아닙니다. 다른 임베딩 모델 추가·유료 API 전송은 이번 범위에 없습니다. 출처 불명의 14/20·18/20 같은 점수는 우리 실측 결과로 사용하지 않습니다.

7. 숫자를 읽는 법

Hit@1: 근거 질문 중 정답 문서를 1위에서 찾은 질문 수 / 근거 질문 수. Hit@3: 서로 다른 상위 3문서 안에서 정답 문서를 하나 이상 찾은 질문 수 / 근거 질문 수입니다. 한 문서의 청크 3개가 문서 3개가 되는 것은 아닙니다.

‘상위3문서 중 정답이 들어 있음’과 ‘근거 있다고 판정해 반환함’도 나눠 봅니다. 순위는 맞아도 보수적인 임계값 때문에 반환하지 않을 수 있습니다. 따라서 순위 Hit와 무근거 혼동표를 함께 기록합니다.

실제 / 판정 근거 있다고 판정 근거 없다고 판정
실제 근거 있음 올바른 수용 필요한 근거를 놓침
실제 근거 없음 위험한 오수용 올바른 거절

벡터는 문서 점수=해당 문서의 청크 최고점으로 하고 top1 >= τ_abs와 top1-top2 >= τ_gap를 모두 만족해야 근거 있음으로 판정합니다. lex는 결과가 없거나 최고점이 τ_lex보다 낮으면 근거 없음입니다. 비교20의 무근거 오수용 0을 제약으로 두고, 그 안에서 필요한 근거를 놓치는 수를 최소화합니다. 동률이면 더 보수적인 임계값을 선택합니다.

10문서에 정답이 정확히 1개이고 균등하게 서로 다른 3문서를 무작위로 고르면 Hit@3의 기대값은 3/10입니다. 이는 가정에 따른 기준선이지 별도 무작위 검색을 실행한 측정값이 아닙니다. 작은 합성 평가셋 결과를 실제 법률 상담 성능이나 일반 한국어 검색 성능으로 확대하지 않습니다.
