# 마스킹 범위 확대 제안 (A3, 제안만)

작성: 2026-11-09. **구현하지 않는다.** 어떤 패턴을 넣을지는 대표 승인 뒤에 정한다.
기준: `mask_personal_data` (Codex 브랜치 `feat/security-input-actions`, `app/security/policy_core.py`). 현재 규칙은 `ID_NUMBER`(주민번호 형식), `EMAIL`, `PHONE` 세 가지이며, 유니코드 정규화한 보기에서 찾고 원문 위치를 치환한다.

## 1. 원칙

- `mask_personal_data(text) -> TextDecision` 계약과 `[NAME]` 치환 형식은 바꾸지 않는다. 규칙만 `_MASK_RULES`에 추가한다.
- 규칙마다 **정상 합성 입력 1 + 오탐 방지 입력 1 이상**을 시험으로 둔다. 일반 숫자(금액, 날짜, 조항 번호)를 가리면 상담 내용이 망가지므로 오탐이 미탐보다 먼저 비용이 된다.
- 공개 저장소이므로 시험 데이터는 전부 합성값이다. 실제로 존재하는 번호를 쓰지 않는다.
- 패턴의 형식(자릿수, 구분자)은 구현 때 공식 형식 자료로 다시 확인한다. 이 문서의 형식은 설계용 가정이다.
- `MASKING_VERSION`을 올리고, 연구 저장소(`Masker` 프로토콜 정본)와 같은 버전으로 맞춘다.

## 2. 후보

| 후보 | 가칭 | 탐지 방식 | 오탐 위험 | 권고 |
| --- | --- | --- | --- | --- |
| 카드번호 | `CARD_NUMBER` | 13~19자리 숫자(구분자 허용) + Luhn 검사 통과 시만 | 낮음 (Luhn이 걸러냄) | **1순위** |
| 사업자등록번호 | `BIZ_NUMBER` | 3-2-5 자리 형식 + 체크디지트 검사 | 낮음 | 2순위 |
| 계좌번호 | `ACCOUNT_NUMBER` | 은행명·"계좌" 같은 문맥어 근처의 숫자열(구분자 허용)만 | 중간 (문맥어 없으면 금액과 구분 불가) | 3순위, 문맥 조건 필수 |
| 사건번호 | `CASE_NUMBER` | 연도 + 사건부호(한글) + 일련번호 형식 | 낮음 | **가릴지 정책 결정 필요** (아래 3) |
| 주소 | `ADDRESS` | 정규식으로 안정적 탐지 어려움 | 높음 | **이번 범위에서 제외**, 한계로 기록 |
| 이름 | `PERSON_NAME` | 정규식으로 불가. 형태소·개체명 모델이 필요 | 높음 | **제외**, 한계로 기록 |

## 3. 결정이 필요한 것

1. **사건번호를 가릴지.** 법률 상담에서는 사건번호가 검색·근거 연결의 핵심일 수 있어, 가리면 기능이 줄고 가리지 않으면 개인 식별 단서가 남는다. 가린다면 `CASE_NUMBER`로 치환하고 근거 ID와 충돌하지 않는지 확인해야 한다. 제안: 이번에는 **가리지 않고** 열린 질문으로 둔다.
2. **계좌번호의 문맥 조건.** 문맥어 목록(은행명, "계좌", "입금", "송금")을 어디까지 허용할지.
3. **주소·이름 미탐을 받아들일지.** 정규식만으로는 못 가리므로, 이 공백은 "마스킹이 보장하는 범위" 문서와 사용자 안내에 명시해야 한다. 안 그러면 "개인정보를 다 가린다"로 오해된다.

## 4. 구현 시 시험 계획 (승인 뒤)

- 규칙별: 합성 양성, 합성 음성(금액·날짜·조항 번호·전화번호와 겹치는 숫자), 구분자 변형, 전각 숫자(정규화 경로).
- 겹침: 한 구간이 두 규칙에 걸릴 때 기존 방식(먼저 잡힌 구간 우선)이 유지되는지.
- 회귀: 기존 `test_policy_actions.py` 등 보안 시험 파일이 기대값 수정 없이 통과.
- 멱등성: 마스킹 결과를 다시 마스킹해도 같다(`[CARD_NUMBER]` 같은 치환 문자열이 규칙에 다시 걸리지 않는다).

## 5. 이 문서가 말하지 않는 것

실제 탐지율과 오탐률은 측정하지 않았다. 형식 가정은 구현 전에 확인해야 하며, 어떤 시험도 아직 없다.
